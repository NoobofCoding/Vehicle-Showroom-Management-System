# MongoDB database schema

MongoDB stores collections of BSON documents, not SQL tables and columns. Mongoose schemas define application validation, field names, defaults, and indexes. The local development configuration uses database `autodesk` at `mongodb://127.0.0.1:27017/autodesk?replicaSet=autodesk`; the URI is kept in the ignored `backend/.env`, never in the frontend. The existing MongoDB service and data directory are retained.

The examples below are documentation only. They are not inserted into MongoDB. ObjectIds and dates use MongoDB Extended JSON notation. Monetary values are integer paise: for example, ₹12,500.00 is stored as `1250000`. The API accepts rupees for the current form controls and converts on the server. Mongoose `Number` values are JavaScript numbers; the BSON serializer stores in-range integral values as BSON Int32 and larger integral values as BSON Double (exact for the safe-integer range used by the application). The application validates paise amounts as safe integers.

## Relationships and business rules

- One vehicle can be referenced by many sales and stock adjustments.
- One customer can be referenced by many sales.
- Sales reference both vehicle and customer ObjectIds and retain embedded snapshots for invoice history.
- Sales use unit selling price, discount, and calculated total in integer paise. The client cannot submit a trusted total.
- Sale stock decrement and sale insertion are performed in one MongoDB transaction. Cancellation changes status and restores quantity exactly once in the same transaction.
- A stock adjustment and stock update are also written in a transaction. Adjustment records have no update/delete API.
- A vehicle with sales or adjustment history, and a customer with sales history, is archived instead of physically deleted.
- Dashboard completed counts/revenue exclude cancelled sales. Physical inventory sums active vehicles' current `stockQuantity`; low stock means quantity less than or equal to each vehicle's threshold.
- Sale/stock write operations require a replica set or mongos. The application rejects these operations with HTTP 503 if the connected deployment lacks transaction support. No partial-write fallback is used.

## Indexes

Every collection has MongoDB's default `_id_` index. The following schema indexes were also verified in the connected local database:

| Collection | Index | Unique? | Purpose |
|---|---|---:|---|
| `vehicles` | `{ vehicleId: 1 }` | Yes | Unique showroom vehicle identifier |
| `vehicles` | `{ status: 1, brand: 1, category: 1, manufacturingYear: 1 }` | No | Inventory status and filters |
| `vehicles` | `{ brand: 1, model: 1 }` | No | Brand/model lookups |
| `customers` | `{ customerId: 1 }` | Yes | Unique customer identifier |
| `customers` | `{ fullName: 1 }` | No | Customer name search |
| `customers` | `{ phone: 1 }` | No | Customer phone search |
| `sales` | `{ saleId: 1 }` | Yes | Unique sale identifier |
| `sales` | `{ vehicle: 1 }`, `{ customer: 1 }` | No | Related history lookup |
| `sales` | `{ saleDate: 1 }`, `{ status: 1 }` | No | Date and status filters |
| `sales` | `{ saleDate: -1, status: 1 }` | No | Recent/status sales listing |
| `stockadjustments` | `{ adjustmentId: 1 }` | Yes | Unique audit identifier |
| `stockadjustments` | `{ vehicle: 1 }` | No | Vehicle adjustment history |
| `stockadjustments` | `{ createdAt: -1 }` | No | Recent adjustment listing |
| `users` | `{ email: 1 }` | Yes | Unique staff login |
| `settings` | `{ key: 1 }` | Yes | Single showroom settings record |

The server initializes Mongoose model indexes at startup. No application-seeded sample business records are created.

## Local Windows replica-set setup

The existing Windows MongoDB service listens only on `127.0.0.1:27017`, uses
`C:\Program Files\MongoDB\Server\9.0\data`, and is configured as the one-node
replica set `autodesk`. The service configuration was updated in place; the
data directory was not moved, reset, or recreated. The application connects to
database `autodesk` using the ignored `backend\.env` URI:

```text
MONGODB_URI=mongodb://127.0.0.1:27017/autodesk?replicaSet=autodesk
```

The `replication` section in
`C:\Program Files\MongoDB\Server\9.0\bin\mongod.cfg` must contain:

```yaml
replication:
  replSetName: autodesk
```

If configuring a new installation, back up `mongod.cfg`, add that setting
without changing `storage.dbPath`, and restart the `MongoDB` Windows service.
Then initialize the replica set only if it has not already been initialized.
From `mongosh` connected to `mongodb://127.0.0.1:27017/admin?directConnection=true`,
run `rs.status()`; only if it reports that no replica set is configured, run:

```javascript
rs.initiate({
  _id: "autodesk",
  members: [{ _id: 0, host: "127.0.0.1:27017" }],
})
```

Wait for `rs.status()` to report a primary. The API health endpoint at
`http://127.0.0.1:5000/api/health` must report `databaseName: "autodesk"` and
`transactions: "supported"`. Do not run the legacy `mongodb:init-dev` helper
against this service; it is restricted to the separate `autodesk_dev` instance
on port `27018`.

Start the API and frontend in separate PowerShell windows:

```powershell
Set-Location C:\Users\bg057\Downloads\project
npm run dev:backend
```

```powershell
Set-Location C:\Users\bg057\Downloads\project
npm run dev:frontend
```

The API and frontend can then be started in separate PowerShell windows:

```powershell
Set-Location C:\Users\bg057\Downloads\project
npm run dev:backend
```

```powershell
Set-Location C:\Users\bg057\Downloads\project
npm run dev:frontend
```

The legacy `mongodb:stop-dev` helper only targets port `27018`; it is unrelated
to the application service on port `27017`.
